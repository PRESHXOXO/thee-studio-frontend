# Prompt Lab — build decisions

Prompt Lab was specified as a standalone Next.js app (own auth, own DB, own design system). Explicit instruction for this build: no changes to Thee Studio's look or name. So Prompt Lab ships as a new screen inside the existing Thee Studio app, reusing its stack, tokens, and conventions instead of the brief's Next.js/Tailwind/Prisma/Vercel stack. Every deviation below follows from that constraint.

- **Stack**: React/Vite screen (`src/screens/PromptLab.jsx`), not Next.js. Engine runs in the existing Python/Gradio backend (`services/prompt_lab.py`), not a Next.js API route — that backend is the only place API keys can live server-side in this architecture, matching how OpenAI/Gemini/Replicate/FAL keys already work.
- **Auth/roles/passcode gate**: dropped entirely. Thee Studio is single-user/local with no accounts anywhere (confirmed in prior audit) — a passcode gate would be the only authed surface in the app and contradicts the existing model. No Owner/Member roles, no `House` screen.
- **Persistence**: `localStorage` (`ts_promptlab`, capped at 30 entries), matching every other history/library store in the app (`ts_library`, `ts_director_history`). No Postgres/Prisma/SQLite — there is no DB anywhere in this app.
- **Images**: reuse the existing `saveToLibrary` → Library screen pipeline (already backed by localStorage + compressed data URLs) instead of Vercel Blob, which doesn't apply outside Vercel.
- **Model**: engine calls OpenAI (`gpt-5.5`, matching the model this codebase already uses for its other OpenAI text/vision calls) via the existing `OPENAI_API_KEY`, switched from the brief's Claude/Anthropic engine at the user's explicit request — one fewer API key to manage, and it reuses billing/setup the user already has. Configurable via `PROMPT_LAB_MODEL` env var on the backend.
- **Design system (Section 9)**: explicitly not applied — instruction was no look/name changes. Prompt Lab uses Thee Studio's existing Miami Sunset dark tokens, `Card`/`Button`/`Icon` components, and monospace-block prompt styling in `--font-mono`, consistent with the rest of the app. No contact-sheet filmstrip, no oxblood/brass palette, no Instrument Serif — those are new-brand-identity elements this task does not authorize.
- **Model adapters (Section 5)**: implemented as `src/lib/promptLabAdapters.js`, a plain metadata/config layer (label, icon, generation availability, craft note per target) rather than the engine itself — the engine (backend) does all target-specific prompt formatting per the brief's system-prompt instructions, since the OpenAI call is doing the actual formatting work, not per-adapter code. The four targets (Gemini/Nano Banana, OpenAI/GPT Image, Sora, Higgsfield) map onto the app's existing generation paths: Gemini and OpenAI generate in-app through the existing `characterGenerate`/`generateImage` functions (Nano Banana and OpenAI engines already exist in this app's Settings/engine list); Sora and Higgsfield are copy-only, since neither has a wired generation path in this codebase yet — the brief's "Higgsfield: fetch live preset list" and video generation are out of scope for a codebase with no video pipeline.
- **Daily generation cap**: dropped. The cap exists in the brief to protect a shared link with one owner's API keys; this app is single-user with the user's own keys, so the existing per-engine key-required gating is the equivalent protection.
- **Content guardrails**: kept in full — default-Black-representation instruction, the "nude" word filter (enforced both in the system prompt and as a hard server-side regex scrub on every string in the response), no real public figures, no sexual/minor content with a refusal path, and the standing negative constraints appended to every generation. These are architecture-independent and preserved exactly as specified.
- **"Why this works" / variants / moods**: implemented exactly as specified in the JSON contract — defensive parsing with fence-stripping and one retry on parse failure, matching the brief's requirement.
